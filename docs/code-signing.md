# コード署名について調べたこと（2026-09-08）

**いまは署名しない。** ADR-0067 はそう決めていて、**却下の理由は費用だけ**だった。
無償で署名を出す仕組み（SignPath Foundation）があるので、**当てはまるかを調べた。**

**結論を先に書く。**

| 問い | 答え |
| --- | --- |
| **いま応募できるか** | **できない。** 未リリースで、実績が無い |
| **将来当てはまりうるか** | **ありうる。** 足りないのは時間と配布の実績であって、設計ではない |
| ⚠ **通れば SmartScreen の警告が消えるか** | **消えない。** 前提が 2024 年に変わっている（下記） |
| **いまの決定を変えるか** | **変えない。** 見直しの条件 8 は**満たされていない** |

---

## ⚠ いちばん重要なこと：署名しても SmartScreen の警告は消えない

**ADR-0067 の見直し条件 8 は「署名があれば SmartScreen の警告が消える」を前提にしている。**
**その前提はもう成り立たない。**

**2024 年 8 月に、Microsoft は EV コード署名の OID を信頼された証明書ルートから外した。**
**いまはすべてのコード署名証明書が同じ扱いになっている。**
OV でも EV でも、**ファイルは自分で SmartScreen の評判を貯めないと警告が出る。**

かつては EV 証明書だけが「署名した瞬間から警告が出ない」扱いだった。
**そこが無くなったので、「署名 ＝ 警告が消える」は成り立たない。**

**評判はダウンロードされて実行された回数で貯まる。**
このソフトは**身内の大会の参加者にしか配らない。**
**評判が貯まるだけの母数がない。**

⚠ **したがって、仮に署名を取れても「配布でいちばん重い障壁」は残る。**
**見直し条件 8 の効果の見積もりを、そこから書き直す必要がある。**

## SignPath Foundation の条件

**証明書は SignPath Foundation の名前で出る。** プロジェクトや個人の名前では出ない。

| 条件 | rematch-observer は | |
| --- | --- | --- |
| OSI 承認のオープンソースライセンス。**商用のデュアルライセンスは不可** | MIT | ✅ |
| **プロプライエタリな部分を含まない** | 依存は .NET と System.Drawing.Common だけ | ✅ |
| 公開されたリポジトリ | setopic/rematch-observer | ✅ |
| **ソースから検証可能な形でビルドされること** | GitHub Actions でビルドしている | ✅ |
| **信頼できるビルド系（trusted build system）**。**オープンソース署名では必須。**<br>使えるのは Jenkins / **GitHub** / GitLab / Azure DevOps / TeamCity / AppVeyor | GitHub Actions | ✅ |
| **積極的に保守されていること** | これから | ⏳ |
| ⚠ **「署名したい形で、すでにリリースされていること」** | **リリースがまだ無い** | ❌ |
| ⚠ **実行するプログラムには「一定の検証可能な実績」を求める**<br>（ライブラリとは区別される） | **配る相手が身内だけで、母数がない** | ❌ |
| **ダウンロードのページか配布先に機能が説明されていること** | README にある | ✅ |

| **マルウェア・ハッキングツールでないこと。**<br>**脆弱性を見つける／突く機能を持たないこと** | どれも持たない | ✅ |
| **利用者のプライバシーや安全を、説明と拒否の手段なく損なわないこと** | ⚠ **下記** | ⚠ |

### ⚠ 「画面を撮るソフト」であることは説明が要る

**マルウェアではないが、説明なしでは疑われる形をしている。**
審査で説明を求められる見込みが高いので、**先に言えるようにしておく。**

**言えることは揃っている。**

- **撮るのはゲームのウィンドウだけで、デスクトップ全体は撮らない**
- **画像は一切外に出さない。送るのは数字だけ**
- **注入もメモリの読み書きも入力の自動送信もしない**
- **送り先は利用者が設定に書いた Webhook だけで、開発者には何も届かない**
- **ソースが全部公開されていて、送信は 1 ファイル（`Webhook.cs`）に閉じている**

**この 5 つは設計の帰結であって、審査のために作った説明ではない**（ADR-0067）。

## 応募すると何を訊かれるか

**応募の書式は短い。**

1. リポジトリの URL（主な開発の場所）
2. ライセンス名と、リポジトリの根にある `LICENSE`
3. **ダウンロードの URL**（GitHub Releases でよい）
4. プロジェクトの説明（何のソフトか、誰が使うか、配る形式）

**通りやすくする準備として挙げられているもの。**

- **コード署名ポリシーの文書**
- `CODE_OF_CONDUCT`
- 根の `LICENSE`
- **README にビルド手順を書く**
- **GitHub Actions の workflow を公開して、ビルドの出どころを示せるようにする**
- 返事のできる連絡先

**このうち 3 つはもう揃っている**（LICENSE / README のビルド手順 / build.yml）。

## 審査にどれくらいかかるか

**公表された期間は無い。**
**最初の接触から組織が作られるまで 2 か月弱かかった例**がある。
**数日から数週間**という書き方もある。**申請の内容と、追加の質問の有無で変わる。**

⚠ **急いで取るものではない。** リリースと実績が先に要る以上、**順番が決まっている。**

## 通らなかった場合に何が残るか

**いまの決定がそのまま残る。**

- **署名しない。SmartScreen の警告は出る**
- **代わりにソースを公開する。**
  画面を撮るソフトを入れてもらう以上、**中身を読めることが唯一の根拠である**
- **単一 exe で、前提の導入も要らない**

⚠ **そして上に書いたとおり、署名を取れてもこの状態はほとんど変わらない。**
**「署名しない」という決定の実質的な代償は、当初の見積もりより小さい。**

## いつ見直すか

**次の 3 つが揃ったときに、もう一度考える。**

1. **リリースが出て、実際に配られていること**（応募の前提）
2. **配布の母数が、評判を貯められる程度にあること。**
   ⚠ **身内の大会だけならここは満たされない。**
   **満たされないなら、署名を取っても警告は消えない**
3. **警告が原因で「入れられない」と言った人が実際に出たこと。**
   出ていないなら、**解こうとしている問題が存在していない**

⚠ **1 だけで応募しない。** 2 が無いまま署名を取ると、
**手間と保守（多要素認証・役割・ポリシーの維持）だけが増えて、警告は消えない。**

**これは ADR-0067 の見直し条件 8 への回答である。**
**条件はいま満たされていない。決定は変えない。**
